# TanStack ファミリーで作る大量データの一覧画面

TanStack DB・TanStack Table・TanStack Virtual を組み合わせて、2 万件のデータを一覧表示するサンプルを作りました。

この発表で話すこと

1. 3 つのライブラリが何をしてくれるのか
2. 今回の構成（どこで何を処理しているか）
3. 実装でつまずいたところ
4. 2 万件のデータで試した結果
5. 実務で使うときの設計の考え方

---

## 1. 使ったライブラリ

### TanStack DB

API から取得したデータをフロントエンド側にコレクションとして保持し、コレクション同士の JOIN や楽観的な更新ができるライブラリです。内部では TanStack Query を使っています。

弊社サービスは API 側に課題があり、リレーションが複雑になってクエリの実行に時間がかかっている印象があります。一覧データを一度取得してしまえば、そのあとはユーザー側でデータの保存とリレーションの組み立てができます。

- UI の面：楽観的な更新で、操作がすぐ画面に反映されるので、ユーザーのストレスを減らせる
- ロジックの面：API を何度も呼ばずに済むので、データの受け取りが速くなる

どうせフロントエンド側で結合するのであれば、バックエンドはリレーションを持たないキーバリューストア（NoSQL）のほうが相性がよいと考え、今回は MongoDB で実装しました。

詳しくは [〇〇さんの記事]() を参照してください。

### TanStack Virtual

大量のデータを一覧に描画するときに使うライブラリです。

1 万件のデータをそのまま描画すると重くなりますが、TanStack Virtual は**画面に見えている行だけ**を DOM にするので、スムーズにスクロールできます。Slack や LINE のトーク履歴はページ分けされていないのにさくさくスクロールできますが、これと同じように、いまどの位置までスクロールしているかを内部で監視して、描画する行を判断しています。

> メリット
>
> - 大量のデータでも描画が重くならない
> - API 側でページングをしなくてもよい

想定される利用ケースとして、プラットフォーム型のサービスとは相性がよいと感じました。

- 就活支援サービスで大量の企業を一覧にする
- EC サイトで商品を大量に並べる
- ログをダッシュボードに表示する

ページ分けをしないと「どこまで確認したか」が分かりにくくなりますが、そこは TanStack Table の絞り込みや並び替えで補えると考えています。

### TanStack Table

多機能なテーブルを作るためのライブラリです。見た目は持たず、ロジックだけを提供します。

- 並び替え（複数列も可）
- 絞り込み・検索
- 列の表示・非表示
- グループ化・行の展開（SQL の GROUP BY のような動き）
- 集計（合計など）
- ページ分け
- 並び替えや絞り込みをサーバー側の API に任せることも可能

> **v9 を使っています。** ネット上の記事の多くは v8（`useReactTable` / `getCoreRowModel`）です。v9 は `useTable` + `tableFeatures` で、使う機能だけを宣言する書き方に変わっています。

個人的には、並び替えや絞り込みを API に任せると、バックエンドである程度データを組み立ててからフロントに渡すことになるので、TanStack DB との組み合わせ方はまだ整理しきれていないと感じました。今後 TanStack DB 側にクエリを投げられるようになると、フロントエンド側でほとんどを解決できるようになると思います。

## 2. 今回の構成

### 技術スタック

| 領域 | 技術 | バージョン |
| --- | --- | --- |
| フロントエンド | React | 19.3.0 |
| | Vite / TypeScript | 8.3.4 / 6.0.3 |
| | @tanstack/react-db（@tanstack/db） | 0.5.8（0.13.0） |
| | @tanstack/query-db-collection | 1.4.3 |
| | @tanstack/react-table | 9.2.8 |
| | @tanstack/react-virtual | 3.14.14 |
| バックエンド | Python / FastAPI / pymongo | 3.14 / 0.143.0 / 4.18.3 |
| DB | MongoDB | 8 |

### データの流れ

```
MongoDB（items / categories）
   │  そのまま保存。JOIN はしない
   ▼
FastAPI（GET /items, GET /categories ...）
   │  条件を付けずに全件返す
   ▼
TanStack DB
   ├ itemCollection（一覧データ 2 万件）
   ├ categoryCollection（カテゴリ）
   └ itemRowsCollection（ライブクエリで JOIN してカテゴリ名を付ける）
   │
   ├──▶ TanStack Table … 並び替え・絞り込み・集計・ページ分け
   ├──▶ TanStack Virtual … 仮想スクロールで全件表示
   └──▶ 仮想化なしのテーブル … 比較用に全件を一度に描画
```

MongoDB には一覧データとカテゴリをひたすら保存し、API ではそのまま抜き出しています。コレクションで一覧データとカテゴリを保持し、ライブクエリでそれらを JOIN します。ここまで条件分岐を一切していないので、受け取るデータ量は少し大きめです。

条件が変わるたびに API を呼ぶと、データの取得と描画が連続で発生してしまいます。UI の変更を柔軟に反映するには、一度に取ってしまうほうがよいと考えました。絞り込みや検索は TanStack Table に任せることで、ユーザーが見たい情報をその場で探せるイメージです。

### 主なコード

ライブクエリで一覧データとカテゴリを JOIN する部分です。

```ts
export const itemRowsCollection = createLiveQueryCollection({
  id: "item-rows",
  query: (q) =>
    q
      .from({ i: itemCollection })
      .leftJoin({ c: categoryCollection }, ({ i, c }) => eq(i.categoryId, c.id))
      .select(({ i, c }) => ({
        id: i.id,
        date: i.date,
        amount: i.amount,
        categoryId: i.categoryId,
        categoryName: c?.name,
      })),
  getKey: (row) => row.id,
});
```

## 3. 実装でつまずいたところ

### TanStack DB

| 症状 | 原因 | 対応 |
| --- | --- | --- |
| 自分で定義した型が合わないというエラー | `@tanstack/react-db` は `Transaction` という名前の型を提供している。同じ名前の型を自分で定義していて、間違って TanStack DB 側を import していた | import 元を自分の型に直す。`Transaction` という型名は避けたほうが安全 |
| `onUpdate` などで「No overload matches this call」 | ハンドラーには変更したデータではなく `{ transaction, collection }` が渡される | `transaction.mutations` から `original` / `modified` / `changes` を取り出す |
| 書き方を直しても型エラーが消えない | `react-db@0.5.7` は `db@0.12.3`、`query-db-collection` は `db@0.13.0` を使っていて、`@tanstack/db` が 2 つ入っていた | `react-db` を 0.5.8 に上げてバージョンをそろえる（`npm ls @tanstack/db` で確認できる） |
| `queryFn` の型エラー | `queryFn` は配列を返す必要がある | `Promise<Item[]>` のように配列を返すようにする |
| 「Join requires an index on "id"」という警告 | JOIN の条件に使う項目にインデックスがない | `collection.createIndex((row) => row.id, { indexType: BasicIndex })` |
| 一部の行に JOIN 先の値が付かない | API が有効なカテゴリしか返しておらず、無効にしたカテゴリと結合できなかった | JOIN 先のデータは、参照される可能性があるものをすべて取得する |

`onUpdate` の書き方の例です。

```ts
onUpdate: async ({ transaction }) => {
  await Promise.all(
    transaction.mutations.map((mutation) => updateItem(mutation.original.id, mutation.changes)),
  );
},
```

### JOIN の種類

`innerJoin` と `leftJoin` で結果が変わります。カテゴリが未設定の行も表示したい場合は `leftJoin` を使います。

| JOIN | 行数 | カテゴリが未設定の行 |
| --- | --- | --- |
| `leftJoin` | 20,001 件（全件） | 263 件が残る（`categoryName` は `undefined`） |
| `innerJoin` | 19,738 件 | 消える |

### TanStack Table

| 症状 | 原因 | 対応 |
| --- | --- | --- |
| 2 万件あるのに 10 件しか表示されない | `paginatedRowModel` を入れると `getRowModel()` は 1 ページ分だけを返す。初期値は `pageSize: 10` | ページ送りの UI を付ける（`nextPage()` / `setPageSize()` など） |
| フッターの合計が少ない | 合計を `getRowModel()`（表示中のページ）で計算していた | 全件の合計なら `getFilteredRowModel()` を使う |

### TanStack Virtual

| 症状 | 原因 | 対応 |
| --- | --- | --- |
| 「Missing attribute name 'data-index'」という警告 | `measureElement` を付けた要素は、何行目かを `data-index` で伝える必要がある | `data-index={item.index}` を付ける |
| 最初の数十行しかスクロールできない | 全行分の高さを確保していなかった。`containerRef` は `directDomUpdates: true` のときしか効かない | 内側に `height: getTotalSize()` を指定し、各行を `position: absolute` + `translateY(item.start)` で配置する |

## 4. 2 万件のデータで試した結果

### テーブルを 3 種類並べて比較

| テーブル | 描画する行 | 特徴 |
| --- | --- | --- |
| TanStack Table（ページ分け） | 1 ページ分（10〜100 行） | 並び替え・絞り込み・集計ができる |
| TanStack Virtual | 画面に見えている行 + 前後 20 行 | 全件をスクロールで見られる |
| 仮想化なし | 20,001 行すべて | 比較用。表示するとかなり重い |

### API の負荷

FastAPI を 1 プロセスで動かし、[oha](https://github.com/hatoo/oha) で負荷をかけました（負荷をかける側とサーバーは同じマシンなので、数字は目安です）。

| 処理 | 1 件あたり | 1 秒あたりの上限 |
| --- | --- | --- |
| 1 か月分の一覧（約 70 件） | 約 3ms | 約 350 件 |
| 1 件の登録 | 約 4ms | 約 550 件 |
| **全件取得（2 万件・3.4MB）** | **約 600ms** | **約 1.7 件** |

- 期間を指定する API は、データを 20 万件に増やしても速度がほとんど変わらなかった（日付のインデックスが効いている）
- 全件取得は、20 万件だと約 3.8 秒・35MB になった
- サーバーを 4 プロセスにすると、1 秒あたりの件数は約 3 倍になった

**TanStack Virtual が軽くしてくれるのは描画だけです。** 通信量やメモリ、API の負荷は減りません。今回のように全件を取る構成は、件数が増えるとここが先に限界になります。

## 5. 実務で使うときの設計の考え方

### 基本方針

**「バックエンドで範囲を絞り、その範囲内をフロントエンドで自由に操作する」** 二段構えにします。

- バックエンド：決めておいた数パターンの条件だけを、認可したうえで高速に返す
- フロントエンド：取得した範囲（ブラウザに載る量）に対して、JOIN・並び替え・絞り込み・グループ化を自由に行う
- 描画：仮想スクロールで、見えている行だけを DOM にする

### 絞り込み条件を 2 種類に分ける

| 種類 | UI | 処理する場所 | 条件を変えたとき |
| --- | --- | --- | --- |
| **範囲条件** | 表の上のフィルタ（期間・ステータスなど） | バックエンド | API を呼び直す |
| **表内操作** | ヘッダーでの並び替え、列ごとの絞り込み | TanStack Table（ブラウザ内） | API は呼ばない |

範囲条件は「ブラウザに載る量まで減らす」ため、表内操作は「載ったデータを自由に見る」ためのものです。

### 役割分担

| 処理 | 担当 |
| --- | --- |
| 認可（見てよいデータだけ返す） | バックエンド |
| 範囲の絞り込み・決まったパターンの並び替え | バックエンド |
| 書き込みの検証・データの整合性 | バックエンド |
| 全期間の集計などの大きな処理 | バックエンド |
| 全文検索 | 検索エンジン |
| 表示用の行の組み立て（JOIN） | TanStack DB |
| 楽観的な更新 | TanStack DB |
| 取得した範囲内での並び替え・絞り込み・グループ化 | TanStack Table |
| 描画 | TanStack Virtual |

### 守るべき原則

- **ブラウザに渡したデータは、ユーザーに見える前提で扱う。** 「全部返してフロントで絞る」は認可の代わりにならない
- **クライアントからの書き込みは信用しない。** 検証は必ずバックエンドで行う
- **バックエンドに任せる条件は数パターンに絞る。** ユーザーの操作をすべてバックエンドに流さない

### NoSQL 側の設計

- **アクセスパターンを先に決め、それぞれにインデックスを用意する**（例：ステータス + 作成日の降順）
- **エンティティごとに分けて保存する。** TanStack DB は正規化されたコレクション同士を JOIN する前提のため
- **キーを統一する。** MongoDB の `_id`（ObjectId）は API で文字列にして返す
- **JOIN 先の列でバックエンド側の並び替えが必要なときだけ、非正規化する**
- Firestore / DynamoDB は読み出し件数で課金されるので、画面を開くたびに全件取得しない

### この構成が成り立つ条件

| 条件 | 成り立たない場合 |
| --- | --- |
| 範囲で絞った件数がブラウザに載る（数千〜1 万件程度） | 範囲をさらに細かくする、または表内操作の一部をバックエンドに移す |
| バックエンドで行う並び替え・絞り込みが数パターンに収まる | RDB を検討する |
| 部分一致検索が取得した範囲内で足りる | 検索エンジンを導入する |

この構成はバックエンドを含めたアーキテクチャ全体に影響するので、一度選ぶと後から戻すのが難しい点に注意が必要です。

## 6. まとめと今後

- TanStack DB で「取得したデータの組み立て」をフロントに寄せると、API の呼び出しを減らして UI を柔軟に変えられる
- TanStack Table と TanStack Virtual で、大量のデータでも操作しやすく、軽く表示できる
- ただし全件を取得する構成には限界があるので、範囲の絞り込みはバックエンドで行うのが現実的

### 今後検討したいこと

- 一覧 API に期間指定やページングを付けて、取得量を抑える
- レンダリング方式：CSR（SPA）か SSR か
- API の方式：REST / GraphQL / RPC
- DB：RDB か NoSQL か
- データの保存場所：メモリ、localStorage（5MB まで）、sessionStorage、IndexedDB、Cookie、Cache API、OPFS、URL のクエリパラメータ
- TanStack DB のコレクションの種類
  - LocalOnly / LocalStorage / IndexedDB
  - リアルタイム同期系：Electric、PowerSync、RxDB、TrailBase
